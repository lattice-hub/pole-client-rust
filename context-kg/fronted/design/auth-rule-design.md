# 鉴权规则编辑 — 设计交接文档

> 适用范围：Pole.IO 治理工作台 → 规则类型 = **鉴权（AuthRule）** 编辑抽屉里的 **「规则」Tab**。
> 本文档描述当前原型的页面交互、前端视图组织、右侧预览映射与保存校验，供后续实现或页面优化参考。
> **重要边界：本设计只调整前端展示、交互组织和预览映射，不调整底层数据结构、后端 schema 或协议契约。** 文中出现的 `scope`、`subRules`、`listType`、`protectedInterfaces`、`strategy.match` 均是当前原型里的前端视图与预览表达。

---

## 1. 设计目标

鉴权规则的核心不是“外部鉴权服务调用配置”，而是围绕指定服务的一组**黑白名单规则**：

- 黑名单接口规则：命中名单后拒绝。
- 白名单接口规则：命中名单后放通。
- 服务级规则：可选兜底规则，接口为空，最多一条，并固定排在最后。

页面需要让用户一眼分清三层关系：

```text
鉴权大规则
├── ① 基础信息
├── ② 服务信息
└── ③ 鉴权子规则
    ├── 黑名单接口规则
    ├── 白名单接口规则
    └── 服务级规则（可选，最多一条，永远最后）
```

关键结论：

1. **服务信息是大规则层字段**，必须作为独立「② 服务信息」板块，放在「① 基础信息」和「③ 鉴权子规则」之间。
2. 「① 基础信息」只放规则名称、启用状态、优先级、描述、标签等通用元信息，不放命名空间 / 服务名称。
3. 「③ 鉴权子规则」只负责黑名单、白名单和服务级规则，不再夹带大规则层服务字段。
4. 外层已经按黑名单 / 白名单分区后，接口级子规则内部不再展示名单类型选择。
5. 服务级规则可以不存在；如果存在，最多一条，固定排在所有接口级规则之后。
6. 名单匹配策略是子规则内部的一段扁平配置，不是独立嵌套卡片。

---

## 2. 页面整体结构

右侧编辑抽屉的「规则」Tab 采用左右结构：

```text
「规则」Tab
├── 左侧：编辑表单
│   ├── ① 基础信息
│   ├── ② 服务信息
│   └── ③ 鉴权子规则
└── 右侧：实时规则预览

底部固定操作栏：校验摘要 + 取消 / 保存并下发
```

视觉体系沿用当前 `index.html` 的 Ant Design 控制台风格：

- 浅灰页面底。
- 白色抽屉表单区。
- 蓝色主操作按钮。
- 状态色 pill 区分黑名单、白名单、服务级。
- 右侧使用代码预览展示 `AuthRule` 视图结果。

## 3. ① 基础信息

基础信息是所有规则类型共用的元信息区域。

建议字段：

| 字段 | 控件 | 说明 |
|---|---|---|
| 规则名称 | 输入框 | kebab-case，例如 `spec-check-traffic-security-20260612` |
| 启用状态 | 开关 | 控制规则是否启用 |
| 优先级 | 数字输入 | 数值越小越先执行，沿用当前规则编辑器约定 |
| 规则描述 | 文本域 | 描述规则意图 |
| 标签 | 标签输入 | 如 `owner:codex`、`scenario:sample` |

基础信息不包含：

- 命名空间。
- 服务名称。
- 受保护接口。
- 黑白名单类型。
- 鉴权服务地址。
- 凭据来源。

---

## 4. ② 服务信息

服务信息是本次新结构的固定独立板块，位置在「① 基础信息」与「③ 鉴权子规则」之间。

标题与说明：

```text
② 服务信息
鉴权规则作用的服务对象
```

字段：

| 字段 | 控件 | 示例 |
|---|---|---|
| 命名空间 | 下拉 | `spec-governance` |
| 服务名称 | 下拉 | `spec-gateway` |

板块说明文案：

```text
该服务下配置黑名单接口规则、白名单接口规则，以及可选的服务级规则；
服务信息属于大规则层，不放进子规则。
```

交互约束：

1. 修改命名空间或服务名称后，右侧预览立即更新 `spec.scope`。
2. 服务信息不进入任意单条子规则卡片。
3. 服务信息不回填到「① 基础信息」里。
4. 服务级规则里的“服务级”只表示子规则接口为空的兜底语义，不等于这里的「② 服务信息」。

---

## 5. ③ 鉴权子规则

标题与说明：

```text
③ 鉴权子规则
先黑名单，再白名单，服务级规则可选且最后
```

内部固定三个分区：

```text
┌ 黑名单接口规则 ─────────────────────┐
│ 命中后拒绝；受保护接口必须写在黑名单或白名单分区里。 │
│ [添加黑名单接口]                                   │
│ 子规则卡片...                                      │
└───────────────────────────────────┘

┌ 白名单接口规则 ─────────────────────┐
│ 命中后放通；接口级名单规则统一放在服务级规则之前。 │
│ [添加白名单接口]                                   │
│ 子规则卡片...                                      │
└───────────────────────────────────┘

┌ 服务级规则 ────────────────────────┐
│ 可选；受保护接口留空时表示整个服务级别，存在时始终位于最后。 │
│ [添加服务级规则] 或 服务级规则卡片                    │
└───────────────────────────────────┘
```

分区规则：

| 分区 | 是否必有 | 可添加数量 | 受保护接口 | 名单类型来源 |
|---|---:|---:|---|---|
| 黑名单接口规则 | 否 | 多条 | 必填，至少 1 个接口 | 外层分区自动映射 `DENY_LIST` |
| 白名单接口规则 | 否 | 多条 | 必填，至少 1 个接口 | 外层分区自动映射 `ALLOW_LIST` |
| 服务级规则 | 否 | 最多 1 条 | 固定为空 | 卡片内选择服务级兜底名单语义 |

保存前至少要有 1 条鉴权子规则。它可以是接口级规则，也可以是服务级规则。

## 6. 接口级子规则卡片

接口级子规则只出现在黑名单接口规则或白名单接口规则分区内。

卡片展开后包含两段：

```text
子规则 [N]
├── 1. 受保护接口
└── 2. 名单匹配策略
```

### 6.1 卡片头

卡片头展示：

- 展开 / 折叠箭头。
- 子规则序号。
- 摘要：`N 个接口 · 1 条名单策略`。
- 状态 pill：
  - 黑名单分区：`黑名单`。
  - 白名单分区：`白名单`。
- 删除按钮。

卡片头不提供名单类型切换。接口级子规则的名单类型由外层分区决定。

### 6.2 受保护接口

说明文案：

```text
接口必须归属黑名单或白名单分区，满足任一接口后进入名单判断。
```

接口表格：

| 列 | 控件 | 说明 |
|---|---|---|
| 协议 | 下拉 | `HTTP / gRPC / Dubbo` |
| 方法 | 下拉 | `GET / POST / PUT / DELETE` 等 |
| 匹配类型 | 下拉 | `完全匹配 / 前缀匹配 / 正则匹配 / 包含 / 不等于` |
| 接口路径 | 输入框 | 如 `/orders`、`/admin` |
| 操作 | 删除 | 同一子规则至少保留 1 个接口 |

分区提示：

```text
所属黑名单分区，提交时自动按 DENY_LIST 映射；
子规则内部不再重复选择名单类型。
```

或：

```text
所属白名单分区，提交时自动按 ALLOW_LIST 映射；
子规则内部不再重复选择名单类型。
```

交互约束：

1. 点击「添加接口」新增一行接口。
2. 接口级规则至少保留 1 个接口。
3. 接口路径不能为空。
4. 删除到最后一行时保留默认空行，避免出现不可编辑状态。

---

## 7. 服务级规则卡片

服务级规则是可选兜底规则，不在黑名单 / 白名单接口分区内。

### 7.1 服务级规则不存在时

服务级分区展示：

```text
服务级规则可以不配置；没有服务级规则时，只按上方黑名单和白名单接口规则生效。
[添加服务级规则]
```

点击「添加服务级规则」后：

1. 新增一条服务级规则。
2. 自动放到所有接口级规则之后。
3. 不允许再添加第二条服务级规则。

### 7.2 服务级规则存在时

服务级规则卡片展开后包含三段：

```text
服务级规则
├── 1. 服务级范围
├── 2. 服务级名单类型
└── 3. 名单匹配策略
```

#### 7.2.1 服务级范围

服务级规则不显示接口编辑表格。

说明文案：

```text
该规则的受保护接口为空，表示服务级兜底规则；
它只能存在一条，并且始终排在黑名单与白名单接口规则之后。
```

预览映射：

```yaml
protectedInterfaces: []
```

#### 7.2.2 服务级名单类型

服务级规则没有外层黑白名单分区，因此需要在卡片内选择自身兜底语义。

| 选项 | 命中结果 | 未命中结果 |
|---|---|---|
| 白名单 | 放通 | 拒绝 |
| 黑名单 | 拒绝 | 放通 |

提示文案：

```text
当前服务级规则：命中放通，未命中拒绝。
名单类型决定命中与未命中时的固定结果。
```

或：

```text
当前服务级规则：命中拒绝，未命中放通。
名单类型决定命中与未命中时的固定结果。
```

## 8. 名单匹配策略

每个子规则内部只有一条名单匹配策略。它是子规则的一部分，不再嵌套成独立可折叠卡片。

展示结构：

```text
名单匹配策略
命中后执行：DENY / ALLOW；未命中执行相反结果。

[AND] [OR] 需同时满足全部条件 / 满足任一条件即命中名单

条件表格：
参数类型 | 参数键 | 匹配类型 | 匹配值 | 操作

[添加匹配条件]
```

### 8.1 不需要的字段

名单匹配策略不包含：

- 策略名称。
- 参数比例。
- 命中动作。
- 未命中默认动作。
- 鉴权服务。
- 鉴权服务异常处理。
- 凭据来源。

### 8.2 AND / OR

| 关系 | 语义 |
|---|---|
| `AND` | 需同时满足全部条件 |
| `OR` | 满足任一条件即命中名单 |

### 8.3 匹配条件

| 列 | 控件 | 说明 |
|---|---|---|
| 参数类型 | 下拉 | `HEADER / QUERY / PATH / COOKIE / METHOD` |
| 参数键 | 输入框 + 候选 | 随参数类型联动候选值 |
| 匹配类型 | 下拉 | `完全匹配 / 前缀匹配 / 正则匹配 / 包含 / 不等于` |
| 匹配值 | 输入框 | 必填 |
| 操作 | 删除 | 至少保留 1 条条件 |

切换参数类型时，参数键自动切换为该类型的默认候选键。

## 9. 前端视图模型

以下结构只用于当前页面组织和右侧预览映射，不代表后端协议调整。

```ts
type AuthViewRule = {
  name: string;
  enabled: boolean;
  priority: number;
  desc?: string;
  tags?: string[];
  scope: {
    ns: string;
    svc: string;
  };
  rules: AuthSubRule[];
};

type AuthSubRule = InterfaceAuthSubRule | ServiceAuthSubRule;

type InterfaceAuthSubRule = {
  type: '黑名单' | '白名单';
  ifaces: ProtectedInterface[];
  strategy: AuthMatchStrategy;
  open?: boolean;
};

type ServiceAuthSubRule = {
  type: '黑名单' | '白名单';
  serviceLevel: true;
  ifaces: [];
  strategy: AuthMatchStrategy;
  open?: boolean;
};

type ProtectedInterface = {
  proto: string;
  method: string;
  path: string;
  op: string;
};

type AuthMatchStrategy = {
  relation: 'AND' | 'OR';
  conditions: MatchCondition[];
};

type MatchCondition = {
  type: 'HEADER' | 'QUERY' | 'PATH' | 'COOKIE' | 'METHOD';
  key: string;
  match: string;
  value: string;
};
```

### 9.1 归一化规则

页面渲染和保存前执行归一化：

1. 黑名单接口规则排在最前。
2. 白名单接口规则排在黑名单之后。
3. 服务级规则如果存在，永远排在最后。
4. 服务级规则最多保留 1 条。
5. 服务级规则的 `ifaces` 强制为空。
6. 接口级规则不允许空 `ifaces`。
7. 旧草稿里如果存在 `strategies[]`，只迁移第一条为单数 `strategy`。
8. 清理旧字段：`fallback`、`strategy.name`、`strategy.ratio`、`strategy.credential`、`strategy.action`、`strategy.failStrategy`。

## 10. 右侧预览映射

右侧预览用于帮助用户理解当前配置，不代表后端 schema 发生变化。

示例：

```yaml
apiVersion: governance.pole.io/v1
kind: AuthRule
metadata:
  name: spec-check-traffic-security-20260612
  enabled: true
  priority: 10
  labels:
    - owner:codex
    - scenario:sample
spec:
  scope:
    namespace: spec-governance
    service: spec-gateway
  description: 调用鉴权样例
  subRules:
    - name: auth-subrule-1
      listType: DENY_LIST
      protectedInterfaces:
        - { protocol: HTTP, method: POST, path: /admin, op: 前缀匹配 }
      strategy:
        match:
          relation: AND
          conditions:
            - { param: HEADER, key: authorization, op: 前缀匹配, value: deny- }
    - name: auth-subrule-2
      listType: ALLOW_LIST
      protectedInterfaces:
        - { protocol: HTTP, method: GET, path: /orders, op: 前缀匹配 }
      strategy:
        match:
          relation: AND
          conditions:
            - { param: HEADER, key: x-user-type, op: 完全匹配, value: internal }
```

存在服务级规则时：

```yaml
    - name: auth-subrule-3
      listType: ALLOW_LIST
      protectedInterfaces: []
      strategy:
        match:
          relation: OR
          conditions:
            - { param: HEADER, key: authorization, op: 前缀匹配, value: Bearer }
```

映射说明：

| 页面位置 | 预览字段 | 说明 |
|---|---|---|
| ② 服务信息 | `spec.scope.namespace` / `spec.scope.service` | 大规则层服务对象 |
| 黑名单接口规则分区 | `listType: DENY_LIST` | 由外层分区自动映射 |
| 白名单接口规则分区 | `listType: ALLOW_LIST` | 由外层分区自动映射 |
| 服务级规则名单类型 | `listType` | 服务级规则由卡片内选择 |
| 受保护接口 | `protectedInterfaces` | 接口级必填；服务级为空数组 |
| 名单匹配策略 | `strategy.match` | 只含 `relation + conditions` |

真实提交到后端时，应按现有后端契约适配，不要求后端直接接受上述预览结构。

## 11. 保存校验

保存前校验：

1. 规则名称需为 kebab-case。
2. 至少配置 1 条鉴权子规则。
3. 服务级规则最多 1 条。
4. 服务级规则如果存在，必须是最后一条。
5. 服务级规则不能配置受保护接口。
6. 接口级规则至少配置 1 个受保护接口。
7. 接口级规则的每个接口路径不能为空。
8. 子规则名单类型必须是黑名单或白名单。
9. 每个子规则必须配置 1 条名单匹配策略。
10. 名单匹配策略至少 1 条匹配条件。
11. 匹配条件的匹配值不能为空。

校验失败时：

- 阻止保存。
- 底部状态展示首条错误。
- Toast 提示首条错误。

## 12. 实现清单

实现侧按当前 `index.html` 的交互结构落地：

1. 保留「① 基础信息」作为通用元信息区。
2. 将命名空间 / 服务名称独立放入「② 服务信息」。
3. 确保「① 基础信息」中不再出现服务字段。
4. 确保「③ 鉴权子规则」只包含黑名单、白名单和服务级规则。
5. 黑名单 / 白名单分区内支持新增、删除接口级子规则。
6. 接口级子规则不展示名单类型选择，名单类型由外层分区自动映射。
7. 服务级规则默认可不存在；存在时最多一条，并固定排最后。
8. 服务级规则不展示接口表格，可选择服务级名单语义。
9. 名单匹配策略作为子规则内部扁平段落展示，不嵌套卡片。
10. 预览和保存前执行归一化，保证顺序与服务级唯一性。

---

## 13. 反回归清单

不要把以下内容加回鉴权页面：

- 把命名空间 / 服务名称放回「① 基础信息」。
- 把服务信息放进任意鉴权子规则卡片。
- 大规则级「受保护接口」全局配置。
- 接口级子规则内部的「名单类型」切换。
- 同一个子规则内部的多条 `strategies[]`。
- 名单匹配策略名称。
- 参数比例。
- 命中动作。
- 未命中默认动作。
- 鉴权服务配置。
- 鉴权服务异常处理。
- 凭据来源。
- 服务级规则强制必填。
- 服务级规则出现在黑名单 / 白名单接口规则之前。
- 将本文档描述成后端 schema 或协议契约变更。

## 14. 验收标准

完成后检查：

1. 鉴权规则左侧结构是「① 基础信息 → ② 服务信息 → ③ 鉴权子规则」。
2. 「② 服务信息」包含命名空间和服务名称。
3. 「① 基础信息」里没有命名空间 / 服务名称。
4. 默认鉴权样例至少包含黑名单接口规则和白名单接口规则。
5. 打开鉴权抽屉时，子规则视觉顺序是黑名单 → 白名单 → 服务级。
6. 接口级子规则内部没有名单类型选择控件。
7. 接口级子规则内部没有策略名称和参数比例。
8. 名单匹配策略不是内层卡片。
9. 服务级规则默认可以不存在。
10. 添加服务级规则后，它始终排最后，且受保护接口为空。
11. 右侧预览中 `scope.namespace` / `scope.service` 来自「② 服务信息」。
12. 右侧预览中黑名单规则映射为 `DENY_LIST`，白名单规则映射为 `ALLOW_LIST`。
13. 保存校验能拦截空接口路径、空匹配值、多个服务级规则。
14. 文案明确说明这是前端交互 / 预览映射，不代表底层数据结构调整。
